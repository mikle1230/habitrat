# HabitRat 游戏化经济系统设计文档

> 📋 **设计参考草案。** 本文档是游戏化经济系统的早期设计提案。双货币模型、装扮系统、等级称号等核心概念已融入权威设计文档，但第 4 节的数据模型字段设计仍有参考价值（部分已实现，部分待后续迭代）。当前权威设计文档请查阅：[HabitRat_产品设计指南.md](./HabitRat_产品设计指南.md)。

## 0. 定位

**核心差异化**：不是"个人自我管理"（Habitica 的模式），而是"**家长辅助、孩子游戏化打卡**"——家长是关卡设计师和审批人，孩子是玩家。游戏化程度对标 Habitica 的丰富度，但审批/监督关系保留，这是这个产品在一堆通用习惯 App 里能立住的地方。

**这次（分享给周边人用的版本）范围**：把"双货币经济 + 等级称号 + 装扮玩法 + 奖励商店分类 + 可配置习惯清单 + 邀请链接"做扎实。RPG 完整角色/装备进阶版、家庭组队副本、真实账号体系、金币银行，都放到验证完这一版之后再做（文档最后有清晰的 Now/Later 分割）。

## 1. 双货币经济模型

这是这次改造的核心，解决"游戏化元素 vs 兑换/惩罚"互相打架的问题。

| | 经验值 EXP | 金币 Coin |
|---|---|---|
| 获得方式 | 每次打卡达标，按习惯配置的 `expValue` 发放 | 同时发放，按习惯配置的 `coinValue`，权重可以独立于 EXP |
| 会不会被扣/花 | **永远不会**，只增不减，也不能被"花掉" | 会，兑换现实奖励、犯错扣分都动这个 |
| 驱动什么 | 等级 / 称号，等级达到某个门槛时**自动免费解锁**小老鼠的新装扮（服饰/伙伴/背景）| 消耗型奖励商店（游戏时间等现实兑换）|
| 心理作用 | "努力的历史记录"，不会因犯错或任何操作被抹去 | "可支配的现实零花钱"，会被惩罚扣减 |

**发放规则**：
- 每个习惯项目配置里有两个数值字段：`expValue`、`coinValue`，两者权重可以完全不同——比如"阅读"这类你更想鼓励"坚持"本身的习惯，可以给更高的 `expValue`（升级更快）但 `coinValue` 正常甚至偏低（避免真实零花钱通胀）。默认两者数值相等，家长可以自己调。
- 连续打卡达标那一刻，EXP 和 Coin 一起结算发放。
- 家长手动加分（`btnBonus`）：默认只加 Coin。如果家长想额外奖励努力本身，UI 上给一个"额外加经验值"的勾选项，默认不勾。
- 扣分（`btnDeduct`）：只扣 Coin，**绝不扣 EXP**。这条是硬规则。

### 1.1 小老鼠的"装扮"玩法

- 单独一个"🐹 装扮小老鼠"场景，展示当前小老鼠的形象（默认形态 + 已装备的服饰/伙伴/背景）。
- 装扮物品（服饰、伙伴、背景）**不能购买，只能靠升级自动解锁**——达到某个等级门槛，新物品自动加入衣柜，全程免费，跟花钱无关。
- 已解锁的物品可以在"衣柜"里自由切换穿戴/更换背景，随便换、不消耗任何东西。
- 首次上线先给 6-10 个等级各配一件解锁物品验证效果，不需要一次性做完整的服装系统。

## 2. 等级 / 称号系统

**目标**：给孩子一个"看得见的成长曲线"，不需要一开始做完整 RPG，先做轻量版验证效果。

- **等级曲线**：`level = floor(sqrt(totalExp / 50))` 这类平方根曲线（前期升级快、给及时反馈；后期需要更多积累，避免"一天点满"）。具体系数可调，建议先按"孩子一个暑假大概能升 5-8 级"去反推系数，让暑假结束时有明显的成长感。
- **称号**：每个等级对应一个称号，比如 Lv.1"习惯新手"、Lv.5"坚持小达人"、Lv.10"自律小能手"……称号可以由家长自定义文案（这是很讨孩子喜欢的细节，比系统写死的称号更有参与感）。
- **升级解锁装扮**：升级到某个等级门槛，自动免费解锁一件新的装扮物品（服饰/伙伴/背景之一），直接进入孩子的"衣柜"，不需要花任何东西、不需要额外操作。
- **进度条 UI**：当前等级 → 下一等级还差多少 EXP，这个视觉反馈比数字本身更能带来游戏感，建议优先做。

## 3. 奖励商店：两个场景分开

- **消耗型（花 Coin）**：现在的兑换项目全部归这一类，逻辑基本不用改（还是现在的"选择要兑换的项目→扣 Coin"流程），只是把字段从 `points` 改成 `coin`。这是"现实向"的场景——游戏时间、零食、外出之类。
- **装扮场景（升级免费解锁，不花钱）**：跟奖励商店是完全不同的两个 screen，不要放在一起，避免孩子混淆"这个到底要不要花钱"。

## 4. 可配置化的数据模型

现在 `HABITS` / `FAMILY` 是写死数组，这次要变成用户在设置页自己配置的列表。设计成**未来能直接映射成数据库表**的形状，即使这一版还是存一整块 JSON：

```
Family {
  id: uuid            // 不要再用"家庭码"直接当主键，码只是邀请凭证
  inviteCode: string  // 邀请码/邀请链接用，可随时重置，不等于身份
  createdAt
}

Member {
  id: uuid
  familyId: uuid
  name: string
  role: 'guardian' | 'child' | 'viewer'   // 替代现在"PIN=家长"的单一权限
  totalExp: number
  level: number (derived, 不需要存，运行时算)
}

HabitTemplate {
  id: uuid
  familyId: uuid
  ownerMemberId: uuid       // 这个习惯是谁的（支持多孩子；也支持"某人做，积分记到另一人账户"的情况）
  rewardTargetMemberId: uuid  // 达标奖励实际记入哪个成员的账户（默认等于 ownerMemberId，但允许不同，比如妈妈的习惯奖励记到孩子账户）
  title: string
  rule: { streakNeed: number, expValue: number, coinValue: number, activeDays: string[] }
  archived: boolean         // 习惯可以停用而不是删除，保留历史记录
}

CheckinLog {
  id, familyId, memberId, habitId, date, status: 'done'|'missed'|'na', effectivePoint: boolean
}

Transaction {
  id, familyId, memberId, type: 'earn_exp'|'earn_coin'|'spend_coin'|'deduct_coin'|'bonus_coin'|'bonus_exp'
  amount, reason, createdAt
}

RewardItem {
  id, familyId, kind: 'consumable' | 'outfit'
  title, cost (仅 consumable 需要), unlockLevel (仅 outfit 需要)
}
```

这一版可以继续整块存 KV/localStorage（结构按上面的形状嵌套即可），但**字段命名和 ID 设计现在就按"以后要拆成数据库表"的标准来**，后续迁移 Postgres 时基本是把这几个数组摊平成表，不需要重新设计模型。

## 5. 邀请机制

- 把"输入 6 位家庭码"升级成"生成邀请链接"（`https://habitrat.app/join/{inviteCode}`），点开链接自动带出加入流程，比手动输码对"分享给朋友"这个场景友好很多。
- 家庭码/邀请码要能随时在设置里重置（防止分享出去的链接被无关人捡到）。

## 6. 后续可以做（这次不实现，先记录想法）

**金币银行 / 利息机制**：如果孩子攒着金币不花，可以像真实银行储蓄一样按一定周期产生利息，鼓励延迟满足、顺便做一点朴素的理财启蒙。这个值得做，但落地前要想清楚几个参数，不建议现在就动手：
- 结算周期（每周结一次？每月？）
- 利率怎么定（固定利率，还是家长可调？）
- 要不要设上限（避免利滚利数字失控、失去真实感）
- 会不会跟"扣分惩罚"产生奇怪的交互（比如刚好在结息日被扣了分，利息算不算）

建议等这一版（装扮玩法 + 双货币经济）验证完、孩子对基础的攒钱兑换已经有感觉之后，再单独设计这个"银行"功能。

## 7. 路线图

**这一版要做（Now）**：
1. 双货币模型改造（EXP / Coin，含发放/扣除规则调整，`expValue`/`coinValue` 按习惯独立配置，支持"某人的习惯、奖励记到另一人账户"）
2. 等级 + 称号（由 EXP 驱动，永不因惩罚倒退）+ 升级自动免费解锁装扮物品
3. 装扮场景（服饰/伙伴/背景三类，靠升级免费解锁，6-10 件起步）与现实奖励商店（花 Coin，不变）分开展示
4. 习惯清单、家庭成员从写死 → 设置页可配置（沿用之前布置的任务）
5. 家庭码 → 邀请链接
6. 分享出去前，加一句简短的使用说明/免责声明（"个人开发的小工具，数据存在开发者服务器，请勿输入敏感信息"）

**先不做（Later，等这版验证完再决定要不要往下走）**：
- 金币银行/利息机制（见第 6 节，需要先单独敲定结算周期、利率、上限等参数）
- 完整角色/装备系统的进阶版（现在的装扮场景先验证 6-10 件够不够）
- 家庭组队/共同任务（类似 Habitica 公会副本）
- 真实账号密码体系（继续用邀请码，但已经按 Now 的模型设计好了，以后换起来不伤筋动骨）
- 多孩子排行榜/对比
- 迁移到真正的 Postgres 数据库（这一版数据量小，JSON 撑得住，但字段设计已经为这一步铺好路）
